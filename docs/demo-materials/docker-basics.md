# Docker 基础知识

Docker 是一种将应用程序及其运行依赖封装为镜像，并以容器形式运行的技术。镜像可以理解为可分发的只读模板，容器则是镜像启动后的运行实例。一个镜像可以启动多个容器；容器中的临时文件通常会随容器重建而消失，因此需要持久保存的数据应放在卷或外部存储中。

构建镜像时，Docker 会依据 Dockerfile 中的指令逐层生成镜像。例如 `FROM` 选择基础镜像，`WORKDIR` 设置工作目录，`COPY` 复制构建所需文件，`RUN` 执行构建命令，`EXPOSE` 说明应用使用的容器端口，`CMD` 或 `ENTRYPOINT` 指定启动程序。镜像层可以被缓存；当某层输入未变化时，构建可能直接复用缓存。因此看到“使用缓存”表示这一层没有重新执行，不等于本轮重新运行了该层对应的测试。

容器端口和宿主机端口是不同概念。比如应用在容器内监听 8080 端口，Compose 可以将宿主机的 8080 映射到容器的 8080。服务之间则通常通过 Compose 网络中的服务名通信，例如 API 可以访问 `db:3306`，而不需要知道数据库容器的动态 IP。端口映射只负责宿主机与容器间的入口，不代表应用内部服务必须公开到宿主机。

Docker Compose 用一个 YAML 文件描述多个协作服务、网络、卷、环境变量和健康检查。`docker compose up -d` 会在后台创建或启动服务；`docker compose ps` 用于查看状态；`docker compose logs` 用于检查日志。`depends_on` 可以控制启动依赖，但只有结合健康检查条件，才可以等依赖服务达到健康状态后再启动依赖它的服务。健康检查只说明探针所检查的条件成立，不一定覆盖业务层全部功能。

持久化卷让数据独立于容器生命周期。例如 MySQL 数据目录挂载到命名卷后，重建数据库容器通常不会删除卷里的表数据。普通 `docker compose down` 会停止并移除 Compose 容器和网络，但保留命名卷；`docker compose down -v` 会同时删除相关卷，可能造成数据不可恢复。因此，在需要保留课程资料、数据库记录或向量索引时，不应随意添加 `-v`。

排查问题时，可以按“服务状态—日志—配置—依赖连通性—业务请求”的顺序检查。先确认容器是否运行且健康，再看对应服务日志；接着核对 Compose 展开后的端口、网络和环境变量配置，最后使用真实 HTTP 请求验证业务行为。开发环境中的演示密码和模型 mock 只适用于本地课堂演示，不应直接作为生产安全配置。
