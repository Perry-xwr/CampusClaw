# LLM 与 RAG 基础

大语言模型（LLM）根据输入文本和上下文生成后续内容。模型输出具有概率性，可能出现资料之外的推断，因此在课程问答中不能只依赖模型参数里记住的知识。RAG（Retrieval-Augmented Generation，检索增强生成）把资料检索放在回答之前：系统先从允许访问的知识库中找出与问题相关的片段，再把问题和片段交给模型生成回答，并返回来源。

知识库通常先把文件抽取为文本，再切分为较小的 chunk。切片大小不能太短，否则背景信息不足；也不能过长，否则会混入大量无关内容并增加模型上下文开销。每个 chunk 应保留材料 ID、班级、切片序号和字符偏移等来源信息。偏移区间可以帮助界面和教师定位片段在原始内容中的位置。文本正文与来源字段适合由关系数据库保存，便于事务、过滤和审计。

向量检索会用 embedding 模型把问题与文本片段映射到向量空间，再按相似度寻找候选结果。分数阈值用于过滤过于不相关的候选；阈值应根据模型和数据验证，不能为了让单个测试通过而随意调低。关键词检索则依据词项匹配与相关度排序，对专有名词、编号和精确短语尤其有用。混合检索可以结合关键词和向量结果，再用 RRF（Reciprocal Rank Fusion）按排名合并候选，避免两类分数尺度不同造成不公平比较。

向量数据库适合存储向量以及检索过滤所需的标识信息，但不应取代正文数据库。系统先从向量库取得候选 ID，再回到正文存储读取 chunk 文本和材料标题，确保引用内容可追溯。检索和问答应始终使用服务端从 Bearer Token 恢复出的 class_id；浏览器提交的班级参数不能决定检索范围。跨班请求应被拒绝或返回不泄露资源存在性的 404。

回答阶段由服务端构造提示词，把当前用户问题、有限数量的 Top-K 证据和引用编号组合起来。客户端不能自行提交 system prompt，也不能把检索边界交给浏览器。回答中的 `[1]`、`[2]` 应对应按顺序返回的 citations；每条引用包含材料标题、chunk 序号、偏移和摘录。若检索没有足够相关的证据，系统应返回明确的“资料中未找到相关内容”，空 citations，并且不调用 Chat Model，以免模型用无依据的常识补全答案。

评估 RAG 时，既要看回答是否通顺，也要核对检索命中是否相关、引用是否真的支持回答、无命中时是否拒答、不同班级是否隔离。模型调用日志可以帮助确认实际发送了哪些证据，但日志应脱敏并限制访问，避免泄露令牌、个人信息或完整私密材料。准确、可追溯和权限正确，比单纯追求回答长度更重要。
